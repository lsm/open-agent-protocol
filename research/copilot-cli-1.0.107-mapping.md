# GitHub Copilot CLI 1.0.107 mapping ledger

The adapter retains the mapping in [the 1.0.98 ledger](copilot-cli-1.0.98-mapping.md), subject to the differences below. This is a schema-based upgrade, not a live recording. The new corpus is synthetic; it copies the prior baseline and adds a case with optional `checkpoint: false` on events. The old live probe belongs only to 1.0.98.

## Comparison and limits

The public CLI repository does not contain the CLI implementation. Its [tag comparison](https://github.com/github/copilot-cli/compare/v1.0.98...v1.0.107) changes documentation and packaging; the npm release assets supply schemas and SDK. The 1.0.107 SDK still sends `session.create`, `status.get` and `session.send`. The published API schema has unchanged `session.send` and `session.abort` parameter fields and required sets, and unchanged `ping` fields. The schema does not define the SDK's `session.create` and `status.get` methods, so their full wire compatibility is not established by that schema.

The event schemas add optional `checkpoint` on event envelopes, optional `causalDependencies` on user messages and tool completions, optional `readOnly` and `mcpServerDisplayName` on tool starts, and optional usage metadata including `responseModel` and cache diagnostics. Tool MCP server-name descriptions now distinguish configured keys and legacy display names. Existing required fields for the compared user, assistant, usage and tool events are unchanged. These additions are not projected by the adapter. The synthetic metadata case covers `checkpoint: false`; checkpoint replay behavior, other added fields, protocol negotiation, real process behavior, authentication, and model responses at 1.0.107 remain unverified. No login, provider call, or real-account fixture was used in this upgrade.

At the data-object level, `UserMessageData` adds `causalDependencies`; `AssistantMessageData`, `AssistantMessageDeltaData`, `SessionIdleData` and `SessionErrorData` have no direct property or required-set changes. `AssistantUsageData` adds `cachePolicyTtlSeconds`, `customToolCallCount`, `inferenceGateway`, `instructionUpdateDeliveryId`, `instructionUpdateLatestEventId`, `orphanToolCallCount`, `promptCacheCreditsBucket`, `promptCacheTtlReason`, `providerType`, `requestBodyCompressionFallback`, `requestBodyCompressionFallbackFrom`, `requestBodyCompressionRejectedStatus`, `responseModel` and `unmatchedToolResultCount`. `ToolExecutionStartData` adds `mcpServerDisplayName` and `readOnly`, and changes the descriptions of `mcpServerName` and `mcpConfigServerName`; `ToolExecutionCompleteData` adds `causalDependencies` and `toolUsage`. None removes a direct property or changes its required set. This comparison does not assert that every recursively referenced definition or unconsumed method is unchanged.

Comparing the SDK's `session.create` request construction directly, the fields the adapters send (`clientName`, optional `model`, `requestPermission`, `requestUserInput`, `workingDirectory`, `streaming`, `envValueMode`) remain present. The SDK adds tool `namespace`, `autopilot`, `trustWorkingDirectory`, `lifecycleDiagnostics`, `sandboxConfig` and `excludedManagedSettings`; it stops sending `enableGitHubCacheStore` and `remoteSession`. The adapters send none of those changed options. Both SDK versions send `{}` to `status.get`; response acceptance at runtime is not established by this static comparison.
