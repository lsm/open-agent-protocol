Open Agent Protocol · schema v0.1

One wire between a control layer and an agent loop

OAP is a CC0 draft protocol plus an executable core that proves it. Everything in the tree serves one invariant: an adapter over somebody else's agent harness must emit event traces the shared validator accepts.

oapGo · ships today · the reference and the oracle
oapxZig · the binary that ships next · port in progress

The shape of it

Two doors, neither downstream of the other

A caller picks a profile, not a product. The agent door speaks sessions and runs; the provider door speaks inferences and parts. One process can open both.

Pick a door

What each profile is for

Agent control

open-agent-protocol.agent-control-core

For
A control layer driving an agent loop it does not own.
Speaks
Sessions, runs, streamed content, tool calls, permission and input interactions, cancellation.
Guarantees
One nonterminal run per session. Contiguous per-run sequence. Exactly one terminal.
Behind it
Its own loop, or any pinned harness via --backend.
oapx serve agent --backend claude

Model provider

open-agent-protocol.model-provider-core

For
A caller that wants one vocabulary across many inference vendors and no agent loop at all.
Speaks
Inference requests, streamed parts, opaque carry, credential grants.
Guarantees
A terminal is the assembly of the parts that ended. Credentials never travel on the wire.
Behind it
Anthropic, OpenAI, Ollama and friends.
oapx serve provider

The thing that makes it a protocol

Every trace goes through three phases

The validator is the arbiter, not a linter. An adapter conforms when the validator accepts what it emits — nothing else counts as evidence.

PHASE 01

decode

Is this JSON, and does any object repeat a key? A duplicate key means two readers disagree about the same bytes.

duplicate_key · malformed_json
PHASE 02

schema

JSON Schema 2020-12 over twelve bundled documents. Envelope types are a discriminated union; extension packs compose new branches into it.

schema_invalid
PHASE 03

semantic

A state machine over the whole trace: admission, sequence, terminals, interactions, capability claims, queue bounds.

53 typed diagnostic codes

Fixtures are normative. fixtures/manifest.json lists 546 traces — positive ones plus invalid ones carrying the exact codes the validator must emit. Change validator behaviour, add a fixture.

A trace, envelope by envelope

What a run actually looks like on the wire

This is fixtures/valid/tools-permission-completed.json, unedited — eleven envelopes covering discovery, admission, a tool call that needs permission, and a terminal. Every field shown is in the file.

request / response pair, outside the run sequence run-scoped event, numbered
→

control layer → endpoint

capabilities.request

Before anything else: what can you actually do? No session yet, no run.

←

endpoint → control layer

capabilities.response

The descriptor, stamped with a revision. From here on, an envelope that exercises an optional feature must cite v1 or be told it is stale. The permission envelope below carries it; the admission and the terminal do not, and need not. native is a real claim: emulated and degraded are the honest alternatives.

{ "type": "capabilities.response",
  "in_reply_to": "capq",
  "capability_revision": "v1",
  "payload": {
    "endpoint": { "id": "agent" },
    "features": {
      "tools":       { "level": "native" },
      "permissions": { "level": "native" } } } }
→

control layer → endpoint

session.message.submit.request

A message for session s1, delivery auto — the caller is not saying whether to start now or queue. That is the endpoint's call to make and report.

←

endpoint → control layer

session.message.submit.response

Admission. The subtlest envelope in the protocol: three fields have to tell one story in three vocabularies. auto resolved to started, which is admission: started, effective_delivery: start, status: running — and the only other whole story is queued / queue / queued. Any other mix is rejected. The run gets its identity here, before it emits anything.

{ "type": "session.message.submit.response",
  "in_reply_to": "req1",
  "payload": {
    "accepted": true,
    "run_id": "r1",
    "requested_delivery": "auto",
    "admission": "started",
    "effective_delivery": "start",
    "status": "running" } }
1

endpoint → control layer

run.started

The run sequence opens at 1 and is contiguous from here. Requests and responses never consume a number — only run-scoped events do.

2

endpoint → control layer

action.call.requested

The agent wants to run shell. execution_owner: agent says who will execute it — a control-owned call would name the control layer instead and resolve down a different path.

3

endpoint → control layer

action.permission.requested

An interaction opens, and it names its own responder. Only user may resolve p1, and only once. The run is now holding something open.

{ "type": "action.permission.requested",
  "sequence": 3,
  "capability_revision": "v1",
  "payload": {
    "interaction_id": "p1",
    "tool_call_id": "t1",
    "requested_by": "agent",
    "responded_by": "user",
    "title": "Allow",
    "choices": [ { "id": "yes", "label": "Yes" } ] } }
4

endpoint → control layer

action.permission.resolved

Granted, by the declared responder. The interaction is settled and the run is free to proceed.

5

endpoint → control layer

action.call.started

The tool call moves through its own lifecycle, tracked per tool_call_id.

6

endpoint → control layer

action.call.completed

It carries a result. A call that ends any other way says so with failed or cancelled — it never simply stops.

7

endpoint → control layer

run.completed

Exactly one terminal per run, and nothing follows it. A run may settle as failed or cancelled before it ever starts — but never as completed.

{ "type": "run.completed",
  "sequence": 7,
  "payload": {
    "run_id": "r1",
    "stop_reason": "end_turn",
    "final_response": {
      "role": "assistant", "content": "ok" } } }

Now break one thing

A sibling fixture, fixtures/semantic-invalid/pending-interaction.json, makes the same mistake one envelope earlier: it opens a user.input.requested interaction i1, then completes the run while i1 is still waiting on its responder. Nothing about any single envelope is malformed; the schema phase passes. The defect only exists across the trace, which is what the semantic phase is for.

The diagnostic names the envelope that broke the rule, the pointer inside it, and the interaction it left hanging. A fixture in the manifest pins that exact code, so an implementation that stops emitting it fails the suite.

Using it

Commands

The Go binary is what you can run today. The Zig one keeps the same verbs and adds a TUI and a one-shot loop.

CommandWhat it does
oap checkCompiles the schemas, runs every fixture, drives the memory adapter demo. The one command that says yes or no.
oap validate trace.jsonValidate a trace you captured. --format=json for machine output.
oap serveHTTP+SSE daemon over the hub: a registry, multi-session fan-out, cursor replay. Loopback only, no auth, single user.
oap serve --stdioThe same hub over newline JSON — twelve ops, each line wrapping an envelope in a transport object.
oap endpointOne agent loop, raw OAP envelopes, one per line. The shape a harness implementing OAP natively takes.
oap conformance --command "…"Spawn somebody's endpoint binary, drive a scripted session, assemble the exchange and run it through the real validator.
oapxThe TUI.
oapx run "fix the failing test"One shot, same loop, no server.
oapx serve agent providerBoth profiles in one process.

Hub and endpoint are different layers. The hub is a multiplexer you talk to; the endpoint is one agent loop that speaks OAP directly. conformance drives the second, not the first.

Claiming conformance

A core profile, then additive units

The core claim covers sessions, one run at a time, streamed content, correlated requests, bounded recovery and the three terminal outcomes. Anything beyond it is a unit you claim by name.

agent-control-core +tools +permissions +user-input +run-controls +tool-sources +control-tools +models +queue +compound-open +steer +btw

Capabilities report effective fidelity — native, emulated, degraded, unavailable — never an idealized harness. An endpoint that emulates a feature says so, and the validator holds it to the claim it made.

Where the port stands

Go is the oracle; Zig is what ships

Both implementations run side by side against the same corpus — 546 fixtures at the time of writing. The Go tree is the answer key until the Zig one reproduces it. Counts move with every merge, so for the live figures run zig build test: the gate prints what it judged and what still disagrees, and zig/src/validation/semantic_gate.zig names each declared exception.

complete1 · TypesWire model and strict decode.
complete2 · SchemaInterpreted, not generated. Every fixture judged or explicitly accounted for.
in progress3 · SemanticLanding unit by unit. The gate names every fixture still disagreeing, so the remainder is always in the tree.
next4 · AdaptersSeven harnesses, ~24k lines, one corpus each.
then5 · OracleRetired, or kept in CI.

There is never a moment without a working product: each stage adds a capability to a binary that already ships. The names stay apart on purpose — differential execution needs both on one PATH, and two executables cannot both be oap.
